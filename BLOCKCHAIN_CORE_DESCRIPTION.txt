                              1. OVERVIEW
================================================================================

Project Name: Blockchain Supply Chain Traceability System
Technology: Hyperledger Fabric 2.5
Consensus: Raft (3 orderers for high availability)
Programming Language: Go 1.19 (Chaincode), Node.js 16 (API)
Database: CouchDB (state), PostgreSQL (off-chain)
Deployment: 100% Docker-based (no local binaries required)

Purpose:
- Track products through entire supply chain lifecycle
- Provide immutable audit trail from manufacture to retail
- Enable two-step handover approval between organizations
- Ensure data integrity with cryptographic signatures
- Support multi-organization collaboration with access control

                          5. DATA STRUCTURES
================================================================================

5.1 PRODUCT
-----------
Primary entity representing physical products in supply chain.

type Product struct {
    ID              string      // Unique identifier (e.g., "PROD001")
    Name            string      // Product name
    Batch           string      // Manufacturing batch number
    Origin          string      // Place of origin/manufacture
    ManufactureDate string      // Date manufactured (RFC3339)
    Status          string      // Current status in supply chain
    Owner           string      // Current owner organization
    CurrentHolder   string      // Current physical holder
    PendingHandover string      // ID of pending handover (if any)
    MetaHash        string      // Hash of off-chain metadata
    Approvals       []Approval  // Array of approval records
    CreatedAt       string      // Timestamp (deterministic from tx)
    UpdatedAt       string      // Last update timestamp
}

Status Values:
- "Manufactured": Initial state after creation
- "HandoverRequested": Handover pending approval
- "InTransit": Being transported by shipper
- "InWarehouse": Stored in warehouse
- "DeliveredToRetailer": At retail location
- "Sold": Final state - purchased by end customer
- "HandoverFailed": Handover rejected, back to sender

5.2 HANDOVER
------------
Represents two-step approval workflow for ownership transfer.

type Handover struct {
    ID                string                 // Format: "HANDOVER-{productID}-{toOrg}"
    ProductID         string                 // Product being transferred
    FromOrg           string                 // Sending organization
    ToOrg             string                 // Receiving organization
    Status            HandoverStatus         // PENDING/ACCEPTED/REJECTED/EXPIRED
    RequestedAt       string                 // Timestamp of request
    RequestedBy       string                 // Identity (CN from certificate)
    FromSignature     string                 // Sender's signature (metadata)
    AcceptedAt        string                 // Timestamp of acceptance
    AcceptedBy        string                 // Identity who accepted
    ToSignature       string                 // Receiver's signature (metadata)
    RejectedAt        string                 // Timestamp of rejection
    RejectionReason   string                 // Reason for rejection
    Metadata          map[string]interface{} // Additional data (waybill, etc.)
}

HandoverStatus enum:
- PENDING: Awaiting receiver approval
- ACCEPTED: Approved, ownership transferred
- REJECTED: Declined by receiver
- EXPIRED: Time limit exceeded (not implemented yet)

5.3 APPROVAL
------------
Records each approval action in the supply chain.

type Approval struct {
    Actor     string                 // Identity performing action
    ActorMSP  string                 // MSP ID of actor's organization
    Action    string                 // Type of action (e.g., "AcceptedHandover")
    Timestamp string                 // When action occurred
    Signature string                 // Digital signature (metadata)
    Metadata  map[string]interface{} // Additional context
}

5.4 SHIPMENT
------------
Tracks transportation details.

type Shipment struct {
    ID          string   // Waybill number
    ProductID   string   // Product being shipped
    ShipperID   string   // Shipper identity
    Waybill     string   // Shipping document number
    Origin      string   // Starting location
    Destination string   // Target location
    Status      string   // Shipment status
    Temperature float64  // Current temperature (for cold chain)
    Locations   []string // GPS tracking history
    CreatedAt   string   // Creation timestamp
    UpdatedAt   string   // Last update timestamp
}

5.5 ORDER
---------
Purchase orders in the system.

type Order struct {
    ID         string   // Order identifier
    ProductIDs []string // Products in this order
    BuyerID    string   // Buyer identity
    SellerID   string   // Seller identity
    Status     string   // Order status
    TotalPrice float64  // Total order amount
    CreatedAt  string   // Creation timestamp
    UpdatedAt  string   // Last update timestamp
}

5.6 HISTORY QUERY RESULT
-------------------------
Structure for returning historical changes.

type HistoryQueryResult struct {
    TxId      string    // Transaction ID
    Timestamp time.Time // Block timestamp
    Record    *Product  // Product state at that time
    IsDelete  bool      // Was this a deletion?
}

================================================================================
                   7. HANDOVER APPROVAL WORKFLOW
================================================================================

Overview:
The handover workflow implements a two-step approval process for transferring
ownership between organizations. This ensures both parties agree to the
transfer before it becomes final.

7.1 WORKFLOW STEPS
------------------

Step 1: Request Handover
┌─────────────────────────────────────────────────────────┐
│ Manufacturer calls: RequestHandoverToShipper()          │
│ - Creates Handover record with status=PENDING           │
│ - Updates Product.PendingHandover = handoverID          │
│ - Updates Product.Status = "HandoverRequested"          │
│ - Emits "HandoverRequested" event                       │
└─────────────────────────────────────────────────────────┘
                            │
                            ▼
Step 2: Accept or Reject
┌─────────────────────────────────────────────────────────┐
│ Option A: Shipper calls AcceptHandover()                │
│ - Updates Handover.Status = ACCEPTED                    │
│ - Transfers Product.Owner to Shipper                    │
│ - Updates Product.Status = "InTransit"                  │
│ - Clears Product.PendingHandover                        │
│ - Adds Approval record to Product.Approvals             │
│ - Emits "HandoverCompleted" event                       │
│                                                          │
│ Option B: Shipper calls RejectHandover()                │
│ - Updates Handover.Status = REJECTED                    │
│ - Records rejection reason                              │
│ - Reverts Product.Owner to Manufacturer                 │
│ - Updates Product.Status = "HandoverFailed"             │
│ - Clears Product.PendingHandover                        │
│ - Adds Approval record with rejection                   │
│ - Emits "HandoverRejected" event                        │
└─────────────────────────────────────────────────────────┘

7.2 HANDOVER FUNCTIONS
----------------------

RequestHandoverToShipper(productID, shipperID, waybill, signature)
Purpose: Manufacturer initiates transfer to shipper
Access: OrgManufacturerMSP ONLY
Validates:
  - Product exists
  - Product status is "Manufactured"
  - Product owned by "Manufacturer"
  - No pending handover exists
Creates:
  - Handover record with ID "HANDOVER-{productID}-SHIPPER"
  - Status = PENDING
  - Metadata includes shipperID and waybill
Updates:
  - Product.PendingHandover = handoverID
  - Product.Status = "HandoverRequested"
Emits: "HandoverRequested" event
Returns: Success or error

AcceptHandover(handoverID, receiverID, signature)
Purpose: Receiver accepts handover and takes ownership
Access: Target organization MSP (OrgShipperMSP/OrgWarehouseMSP/OrgRetailerMSP)
Validates:
  - Handover exists
  - Handover status is PENDING
  - Caller MSP matches handover.ToOrg
Updates Handover:
  - Status = ACCEPTED
  - AcceptedAt = current timestamp
  - AcceptedBy = caller identity (from certificate)
  - ToSignature = provided signature
Updates Product:
  - Owner = handover.ToOrg
  - CurrentHolder = handover.ToOrg
  - Status = new status based on organization:
    * Shipper: "InTransit"
    * Warehouse: "InWarehouse"
    * Retailer: "DeliveredToRetailer"
  - PendingHandover = "" (cleared)
  - Adds Approval record to Approvals array
Emits: "HandoverCompleted" event
Returns: Success or error

RejectHandover(handoverID, reason, signature)
Purpose: Receiver declines handover
Access: Target organization MSP (OrgShipperMSP/OrgWarehouseMSP/OrgRetailerMSP)
Validates:
  - Handover exists
  - Handover status is PENDING
  - Caller MSP matches handover.ToOrg
Updates Handover:
  - Status = REJECTED
  - RejectedAt = current timestamp
  - RejectionReason = provided reason
Updates Product:
  - Owner = handover.FromOrg (reverted)
  - CurrentHolder = handover.FromOrg (reverted)
  - Status = "HandoverFailed"
  - PendingHandover = "" (cleared)
  - Adds Approval record with rejection details
Emits: "HandoverRejected" event
Returns: Success or error

GetHandover(id)
Purpose: Query handover details
Access: Any organization
Returns: Handover struct or error

GetPendingHandoversForOrg()
Purpose: List pending handovers for caller's organization
Access: Any organization
Logic:
  - Determines caller's MSP ID
  - Queries all handovers with prefix "HANDOVER-"
  - Filters by ToOrg == caller's org AND Status == PENDING
Returns: Array of Handover structs

                       8. SECURITY & ACCESS CONTROL
================================================================================

8.1 MULTI-LEVEL SECURITY
-------------------------

Level 1: Fabric Framework (Automatic)
- X.509 Certificate Authentication
- ECDSA Digital Signatures (P-256 curve, SHA-256 hash)
- TLS for all peer-to-peer communication
- MSP-based identity management
- Transaction signatures validated before execution

Level 2: Endorsement Policy
- Policy: MAJORITY (3 out of 4 organizations)
- All transactions require 3 endorsements
- Single organization cannot manipulate data alone
- Distributed trust model

Level 3: Chaincode Access Control
- MSP-based role validation in every function
- Organization-specific permissions enforced
- Helper functions: isManufacturer(), isShipper(), etc.

Level 4: Application Signatures (Metadata)
- Signature fields in Handover and Approval structs
- Currently stored as strings (audit trail)
- NOT cryptographically verified (Fabric handles tx signatures)
- Purpose: Additional traceability, future enhancement

8.4 VALIDATION FLOW
--------------------

1. Client submits transaction with private key signature
2. Fabric SDK validates certificate chain
3. Peer verifies ECDSA signature matches certificate
4. Peer checks MSP membership
5. Chaincode validates organization permissions
6. Endorsing peers sign response
7. Client collects endorsements (need 3/4)
8. Orderer validates all signatures
9. Block committed only if all signatures valid

11.1 SCHEMA
-----------

Schema File: offchain/postgres/schema.sql

Tables:

products (metadata)
- id VARCHAR(50) PRIMARY KEY
- name VARCHAR(200)
- batch VARCHAR(100)
- origin VARCHAR(200)
- manufacture_date DATE
- current_status VARCHAR(50)
- owner VARCHAR(100)
- meta_hash VARCHAR(100)
- created_at TIMESTAMP
- updated_at TIMESTAMP
- INDEX: idx_products_status
- INDEX: idx_products_batch

pending_handovers
- id VARCHAR(100) PRIMARY KEY
- product_id VARCHAR(50) REFERENCES products(id)
- from_org VARCHAR(50)
- to_org VARCHAR(50)
- requester_signature TEXT
- waybill VARCHAR(100)
- status VARCHAR(20)
- requested_at TIMESTAMP
- INDEX: idx_pending_handovers_status
- INDEX: idx_pending_handovers_product

handover_approvals
- id SERIAL PRIMARY KEY
- handover_id VARCHAR(100)
- approver_org VARCHAR(50)
- approver_id VARCHAR(50)
- signature TEXT
- action VARCHAR(20)
- approved_at TIMESTAMP
- INDEX: idx_handover_approvals_handover

shipments
- waybill VARCHAR(100) PRIMARY KEY
- product_id VARCHAR(50) REFERENCES products(id)
- shipper_id VARCHAR(100)
- origin VARCHAR(200)
- destination VARCHAR(200)
- status VARCHAR(50)
- temperature DECIMAL(5,2)
- created_at TIMESTAMP
- updated_at TIMESTAMP

shipment_locations
- id SERIAL PRIMARY KEY
- waybill VARCHAR(100) REFERENCES shipments(waybill)
- location VARCHAR(200)
- timestamp TIMESTAMP
- INDEX: idx_shipment_locations_waybill

orders
- id VARCHAR(100) PRIMARY KEY
- buyer_id VARCHAR(100)
- seller_id VARCHAR(100)
- status VARCHAR(50)
- total_price DECIMAL(12,2)
- created_at TIMESTAMP
- updated_at TIMESTAMP

order_items
- id SERIAL PRIMARY KEY
- order_id VARCHAR(100) REFERENCES orders(id)
- product_id VARCHAR(50) REFERENCES products(id)
- quantity INT
- price DECIMAL(12,2)

notifications
- id SERIAL PRIMARY KEY
- organization VARCHAR(50)
- type VARCHAR(50)
- message TEXT
- reference_id VARCHAR(100)
- is_read BOOLEAN DEFAULT FALSE
- created_at TIMESTAMP
- INDEX: idx_notifications_org
- INDEX: idx_notifications_read

13.4 BACKUP & RECOVERY
----------------------

Critical Data to Backup:
1. Crypto materials: network/crypto-config/
2. Channel artifacts: network/channel-artifacts/
3. Chaincode source: chaincode/go/
4. Configuration files: network/*.yaml
5. PostgreSQL database: pg_dump
6. API wallet: apps/gateway-nodejs/wallet/

Disaster Recovery:
1. Restore crypto materials
2. Restore configuration files
3. Run bootstrap-docker.ps1
4. Restore PostgreSQL database
5. Restore API wallet
6. Verify network connectivity

Ledger Recovery:
- Blockchain data is immutable
- Each peer has complete ledger copy
- Orderers maintain Raft log
- If peer fails, rejoin channel to sync
- If all peers fail, recover from snapshot + Raft log
